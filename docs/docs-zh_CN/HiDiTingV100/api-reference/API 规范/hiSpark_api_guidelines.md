# HiSpark API 设计规范


## 目的及范围

HiSpark API是提供给开发者在编程界面上的定义，体现了HiSpark架构软件能力范围。

本文档主要介绍对应用开放的外部API，其设计定义规则，以推进HiSpark架构的生态发展，保证开发者的使用体验。

本设计规范主要用于约束如下跟架构层级对应的外部API：内核驱动类接口，及系统业务类接口
编程语言维度，当前含C接口，CPP接口

## 基于生态解决方案的API分类
* 内核、驱动类接口
* 系统、业务类接口

分类下的业务领域概况

| 分类           | 业务领域                | 
| -------------- | ------------------- |
| 内核，驱动 | kernel, drivers  |
| 系统，业务 | ai, bts, gnss, media, graphic, nfc,<br> at, crc, diag, nv, partition, transmit, upgrade, psa, ipc_fs,<br> ohos JS, Native|


## 模块及其封装规则
结合当前生态解决方案及分层，其主要模块的一些封装规则
* 1. LOS接口需封装为osal接口
* 2. osal 接口不再封装，应用层可直接调用。(便于小型化)
* 3. 涉及开源组件标准接口，不再封装
* 4. 某些领域含不同层级接口。不同场景或产品形态对不同层级接口调用的约束做好限定。待于产品对齐
（例如，蓝牙子系统封装了L2, L3接口。某类场景下的客户建议只调用一种接口，不可L2,L3混用。）


## 头文件路径管理规则
内核对外头文件路径置于    <Root>/kernel 目录对应路径下
驱动对外头文件路径置于    <Root>/include/driver 目录对应路径下
系统、业务类头文件路径置于 <Root>/include/middleware  目录对应路径下

当前现状，为简化评审流程，适应快速迭代更新，部分系统、业务类头文件分布在组件实现目录下。
如：
Media 路径：    <Root>/middleware/services/media/foundation
Graphic 路径：  <Root>/middleware/services/gui/uikit
BTS L3 路径：   <Root>/protocol/bt/host/include/bs_service

以上对外头文件路径可作为工程管控白名单参考。

## 命名规则

### C接口
#### 函数命名
* **格式** 
uapi_<模块名>_<功能描述>
* **风格**
全小写，单词间用下划线 “_” 分隔。
模块名直接关联功能领域。
* **样例**
uapi_avplay_create：创建 AV 播放器
uapi_avplay_get_vdec_capability：获取视频解码能力
uapi_cc_set_attr：设置 CC 属性

#### 结构体类型命名
* **格式** 
uapi_<模块名>_<语义描述>
* **风格**
与接口函数命名风格一致，保持小写和下划线 “_” 分隔。
* **样例**
uapi_avplay_attr：AV 播放器属性结构体
uapi_video_frame_info：视频帧信息结构体
uapi_cc_attr：CC 模块属性结构体

#### 宏定义命名
* **格式** 
UAPI_<模块名>_<语义描述>
* **风格**
全大写，单词间用下划线 “_” 分隔，用于标识常量或事件类型。
* **样例**
UAPI_AVPLAY_EVENT_VID_LAST_FRAME_FLAG：视频最后一帧标志事件
UAPI_ACODEC_FORMAT_MP3：音频编码格式常量

#### 枚举类型命名
* **格式** 
uapi_<模块名>_<语义描述>
* **风格**
与结构体类型命名规则一致，保持小写和下划线分隔。
* **样例**
uapi_hdmirx_it_content_type: HDMI 内容类型枚举
uapi_avplay_media_chan: 媒体通道类型枚举

### CPP接口
#### 类命名
* **格式** 
<模块名><子模块名>
* **风格**
采用大驼峰式命名法 (PascalCase)，单词首字母大写。
模块名直接关联功能领域。
* **样例**
AudioPlayer
AudioManager
ImageLoader
UI3DCylinder
UICrossView
UIMapView

#### 函数方法命名
* **格式** 
<功能描述>
* **风格**
采用大驼峰式命名法 (PascalCase)。
* **样例**
Play
Pause
Stop
GetAutoPlay
IsPlaying


#### 成员变量命名
* **格式** 
<语义描述>
* **风格**
私有成员变量使用小驼峰命名法 ，并以下划线 _ 结尾，以区别于函数参数。
* **样例**
double volume_;
bool autoPlay_;
bool isRunning_;

#### 宏定义命名
* **格式** 
<语义描述>
* **风格**
全部大写，单词间以下划线分隔。

#### 枚举类型命名
* **格式** 
<模块名><语义描述>
* **风格**
枚举类型名大驼峰，
枚举值使用全部大写加下划线。

* **样例**
枚举值使用全部大写加下划线。
*enum class AudioPlayerLoopMode : int32_t {
    AUDIO_PLAYER_PLAYLIST_LOOP,
    AUDIO_PLAYER_PLAYLIST_PLAY,
    AUDIO_PLAYER_SINGLE_LOOP,
    AUDIO_PLAYER_INVAILD_LOOP,
};*


## 注释规则
### 注释分类
注释在此分为两类
* 传统风格注释，不用于文档生成；
* 文档类注释，遵循Doxygen文档生成工具规范，自动提取注释内容生成API参考。

|| 注释类型           | 标记                |场景|
|--| -------------- | ------------------- |----|
|1| 无需生成在文档内 | 使用传统风格：<br> 1.  /* <注释内容> */ <br>2.  // <注释内容>  | copyright、日期、作者等信息|
|2| 需生成在文档内 | /**  <注释内容> */| 模块、文件、变量/常量、结构体/联合体、枚举、方法、类型/宏定义|

### 文档类注释规范
如下逐一介绍体现在API文档中注释的内容/格式规范
#### 模块 Module
* **规范**
1. 使用 "@addtogroup 模块名"标识
2. 如需将头文件中函数划分到该模块中，则在函数前使 addtogroup 标记，使用“ @{ ”、" @} " 将该函数包起
3. 一个模块下若含多个头文件，各头文件 addtogroup需保持完全一致(含空格标点等)，否则将含多段注释

* **标记名称及说明**
@brief 简要描述该库的作用
@since 起始版本

#### 文件 File
* **规范**
1. 使用 "@file 文件名"标识
2. 文件名必须和实际文件命名保持一致
3. 文件注释置于代码前。
4. 若有多个段落，每段须以“\n”结束
5. 中间注释内容段中，"*"前后需留有一空格

* **标记名称及说明**
@brief 简要描述该头文件的作用
@library 引用头文件接口时，需要链接的 so 名字。
@syscap 头文件所属的syscap 能力。
@since 起始版本。

#### 变量/常量
* **规范**
1. 注释置于代码前
2. 若有多个段落，每段须以“\n”结束

* **标记名称及说明**
@brief 简要描述该宏定义、常量的含义
@deprecated 涉及废弃时写。需写明如何替代

#### 结构体/联合体
* **规范**
1. 针对其成员，需对每一个成员的含义进行说明；
2. 注释置于成员前
3. 若有多个段落，每段须以“\n”结束

* **标记名称及说明**
@brief 简要描述该结构体/联合体的含义
@deprecated 涉及废弃时写。需写明如何替代

#### 枚举
* **规范**
1. 针对枚举值，需对每一个枚举值的含义进行说明
2. 注释置于枚举值前
3. 若有多个段落，每段须以“\n”结束

* **标记名称及说明**
@brief 简要描述该枚举的含义
@deprecated 涉及废弃时写。需写明如何替代

#### 方法
* **规范**
1. 简要描述和详细描述之间需要空行。
2. 详细描述中，若有多个段落，每段须以“\n”结束
3. 需包含@param 标记参数，一个参数使用一个@param标记
4. 需包含@return 标记返回值，一个函数只可以使用一个 @return 标记。返回值描述介绍返回值的含义。

* **标记名称及说明**
@brief 简要描述该函数的作用
@param 参数名，参数描述（使用空格分隔）
参数描述需要包含如下信息：参数的作用、使用限制和建议；参数的取值范围，以及取到边界值、非法值的后果。
@return 返回值描述。
对此函数会返回的每个返回值说明其含义。若该函数没有返回值，则删除该标记
@see 当存在与该函数相关联的函数，可通过@see建立到参考函数的链接
@permission 对权限有要求的接口需说明
@deprecated 涉及废弃接口时写。
@useinstead {@link 新接口名}

### 规范说明
以下对每一条规则逐一进行阐述
* **易用性**
  * 1：符合编码规则
  满足所属项目，对应编程语言的相关编码规范。
  如：编码风格，大小写，连字符，下划线，前缀等规则
  <br>  
  * 2：准确使用英语语法
  准确使用类名，模块名的名词表述。
  功能行为准确使用动词或者动宾结构。(注意及物、不及物动词)
  <br>

  * 3：合理使用缩写
  尽量避免使用缩写。
  如需，则使用业界标准缩写。避免自创含义不清，及易混淆缩写。
  <br>

  * 4：遵循成对性
  合理设计需成对出现的API
  命名使用标准对仗词(英语语法标准对仗)
  如，有init, 需有deinit 
  <br>

  * 5：准确体现设计架构模式
  若需体现设计模式，则需准确使用标准术语。
  如 Factory, Builder, Singleton
  <br>

  * 6：避免争议名词
  避免使用争议名称引起法律，宗教、种族等问题
  <br>

  * 7：参数类型合理
  便于扩展。可使用结构体参数类型，便于新增参数字段，无需改动接口本身。
  <br>

  * 8：参数数量合理
  参数数量控制在5个以内，遵循编程规范
  <br>

  * 9：参数顺序合理
  通常以先入参，后出参数；
  根据参数重要性、逻辑顺序排列；
  可选参数置于必选参数之后
  <br>

  * 10：返回值定义完备
  正常情况返回值覆盖全面；
  及考虑异常和无效情况，便于开发者合理处理
  <br>
  
  * 11：异常处理合理
  异常情况下的特殊返回定义准确，且在同一模块，同类业务有统一定义；
  如输入参数无效、内存失败、资源耗尽等
  <br>

  * 12：正向逻辑表达
  正向逻辑表达	接口的命名尽量使用肯定方式的表达，而非否定方式的表达
  <br>

  * 13：降低出错可能性
  多个参数传递时，表达含义明确易懂，组织合理。降低误传，漏传等情况的可能性。
  <br>

  * 14：控制顺序耦合
  若方法函数需要按照某特定顺序调用才可正常工作，则对使用者要求较高，易出错。避免模块间依赖过于复杂。
  <br>

  * 15：准确表达逻辑功能
  接口名称准确描述其所完成的操作及功能；
  避免“隐藏”接口名未体现的操作；
  若包含操作过多，则需进一步拆分；
  <br>

  * 16：良好封装性
  注意封装，不过多暴露实现细节，硬件信息，算法种类
  <br>

  * 17：单一职责
  保证单一核心职责。
  根据封装层级，只做一件事情。
  <br>

* **可用性**
  * 18：保证可靠性
  须针对所有情况进行准确定义，相应情况按照定义的行为完成工作。
  若未按预定行为返回结果，或无故产生程序崩溃异常，均属不可靠行为。
  <br>

  * 19：功能完备性
  不应出现在支持的范围内，某个流程中断，或某个选项缺失的情况发生。API设计者应做好足够的验证和推演
  <br>

  * 20：权限与隐私保护性
  涉及到用户数据、用户隐私的接口都必须做好权限限制和数据保护
  <br>

  * 21：考虑并发环境
  尽可能避免出现线程不安全的问题
  <br>

  * 22：资源管理闭合
  若接口包含动态资源的申请，也需要考虑到资源的释放
  <br>

  * 23：考虑逻辑可重试
  对于可能失败的接口，考虑好给开发者相应的机制来重试。
  可提供接口给开发者查询是否可用，或提供状态监听机制，且对最大重试次数进行说明
  <br>

  * 24：满足幂等性
  多次和一次请求某一个资源应该具有同样的效果
  <br>

  * 25：设备通用性
  接口的设计应具有面对多种设备，不同产品形态的适用性。
  如对于用户输入事件，考虑不同的用户交互方式：触摸、按键、语音等。
  <br>

* **一致性**
  * 26：术语概念一致
  术语和概念的一致性。
  每个概念应对应唯一术语，定义精准、无二义；应遵循业界已有通用术语。
  <br>

  * 27：设备间行为一致
  同一接口在不同的设备上应当保证行为是一致的
  <br>

  * 28：版本演进一致
  接口应保证在系统版本演进的情况下，其行为是一致的。
  接口行为变更不能影响已开发的应用。
  <br>

  * 29：命名风格一致
  指代同一内容时，应该使用相同的命名
  <br>

  * 30：参数顺序一致
  同一个命名空间或同一个模块来说，其成套的接口的参数顺序应保持一致
  <br>

  * 31：同步/异步风格一致
  异步接口应可通过入参和返回值判断出，风格上要保持统一。
  若同时提供同步和异步接口，则通过后缀 sync /async 加以区分。
  <br>

* **兼容性**
  * 32：新旧系统版本兼容性
  变更要保证向后兼容原则。
  废弃API要在源码和文档中以 deprecated 进行标识，并引导开发者使用变更后的API。
  废弃API需保留5个版本，保证其功能仍然可用。充分告知并给予开发者充分时间过渡更新后，方可删除。
  <br>

  * 33：二进制向后兼容性
  已有程序不用重新编译可正常链接、运行。
  保证在版本升级的情况下，对象实例的内存布局不会发生变化。
  如，若有结构体更新，则新增变量置于现有变量后
  <br>

* **文档及资料**
  * 34：注释规范化
  遵循文档生成工具的规范，便于自动化生成。 (如 Doxygen语法)
  模块，文件，结构体，联合体，枚举，变量，方法等信息覆盖全面
  <br>

  * 35：使用场景说明清晰
  接口说明清楚使用场景，如产品形态等信息；
  <br>

  * 36：接口说明准确
  真实准确反映代码行为。
  若接口在不同版本间存在行为变化，需针对情况做详细说明。
  对于废弃接口，需明确标记，做好替代接口说明。
  <br>

  * 37：参数说明准确
  对于API每一个参数，应提供清晰说明。
  其含义，取值范围，是否为必选参数，或可选参数允许为空。若为枚举类型，其每个枚举值的使用场景
  <br>

  * 38：返回值/异常说明准确
  若接口有返回值/异常，需要在接口说明中描述完整
  <br>

  * 39：元信息完备
  元信息描述了API自身的基本信息。如自哪个版本启用，系统能力，当前可用性。
  工具和SDK会利用这个信息进行相应的处理，如完成静态检查，兼容性管理和自动提示。
  例如：针对已经废弃的接口会给出警告提示
  <br>

  * 40：风格一致
  API的说明资料，在风格和样式上保持一致
  <br>

* **组织方式**
  * 41：分层合理
  结合架构模型的分层，接口设计也要对应其相应层次。
  如基于当前HiSpark架构分层的接口可分为：
  -内核、驱动类接口
  -系统、业务类接口
  <br>

  * 42：模块划分合理
  需关注水平层面分层，也需关注垂直层面划分。
  合理组织，命名中体现模块归属。如 UAPI按功能模块可划分为 avplay, cc, hdmirx
  <br>

  * 43：对外开发机制管理规范化
  接口不仅是编程接口，公开给开发者的机制也属API一部分。如应用描述文件 json, xml, yml等，需按接口规范规则管理。
  <br>

* **质量属性**
  * 44：性能满足要求
  及时响应，避免调用者等待。调用执行耗时过长应设计为异步方式
  存在大量数据传输时，考虑使用共享内存，消息队列等
  对使用资源的API调用时需能及时释放资源，异常场景设计好容错机制，保证资源释放
  <br>

  * 45：功耗设计合理
  涉及无源设备，考虑功耗合理设计，对于高功耗接口提供充足说明及开发指导。如锁屏或应用切入后台后，停止高功耗行为。
  <br>

  * 46：可测试性
  新增API须同步交付API自动化测试用例。
  用例场景单一，单条用例覆盖接口单个功能场景。
  用例执行可自动化
  <br>

  * 47：环境适应性
  便于用户个性化，提供环境自定义能力，在未指定参数的情况下，能根据当前所属环境，自适应的返回相应环境下的结果。
  <br>

* **稳定性**
  * 48：降低接口废弃率/变更率
  以保持长期稳定，持续兼容为API设计的目标。降低开发者的维护成本。
  <br>

* **安全性**
  * 49：避免接口被滥用
  接口的使用超出了原先预期的限制。含数量上的滥用，范围上的滥用。
  需一定机制进行防范。如仅一次授权防止数量滥用，或根据用户身份进行相应限制。
  应在接口说明中描述清，并在检测到滥用行为时，返回值告知调用者。
  <br>

  * 50：避免接口被利用
  接口被用来造成负面影响，例如攻击系统。
  对某接口，或接口组合的调用导致系统崩溃，或进入不可预期状态，或导致安全问题，则接口存在问题。需合理设计，全面考虑场景。
  <br>

* **可维护性**
  * 51：可承载业务能力演进
  某些大规模特性，需经数次迭代才能打磨完成。须在设计上考虑扩展性。
  随能力的演进，避免在新版本上开发一组新接口，而废弃原先的接口。
  <br>
  * 52：功能扩展不影响已有行为
  应因新场景的引入，而破坏原先存在的行为。
  如接口新增参数，或某参数新增选项值，要考虑清对已存在行为的一致性。
  <br>
  
  * 53：文档资料配套更新
  更新接口实现时，配套更新接口说明。
  <br>

* **不可替代性**
  * 54：API之间正交
  多个接口之间不应该出现重合的功能。
  若功能出现重叠交错时，应将新接口功能进一步拆分。考虑合理重构。
  <br>

* **开发者反馈**
  * 55：关注开发者反馈
  持续关注开发者的反馈。识别并改进问题。如
  开发者需更多API满足功能场景。
  开发者反馈的接口设计合理性问题。(命名、参数设置)
  开发者反馈的接口行为与文档描述不一致。
  开发者无需的冗余接口。
  <br>
